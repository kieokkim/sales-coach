# DECISION_LOG 기록 제안

이 프로젝트는 "문제 → 가설 → 설계 → 측정 가능한 KPI" 서사를 포트폴리오 축으로 삼는다.
그 서사의 원자재가 DECISION_LOG다. 결정의 **이유와 버려진 대안**이 기록되어야
나중에 "왜 이렇게 만들었나"에 답할 수 있다.

## 언제 기록을 제안하는가

다음이 확정되는 순간, 코드 작업과 별개로 기록을 제안한다:
- 아키텍처 변경 (노드 추가/분리/통합, 모듈 구조 변경)
- 라이브러리·모델 선택 (예: MiniLM→bge-m3, GPT-4o-mini vs Groq)
- 스키마·데이터 구조 변경 (예: top_issue → top_issues+tradeoff)
- 접근법 전환 (예: 코호트 분석 포기 → 구매 패턴 분석)
- eval 방법론 결정 (예: 51.6%에서 의도적 중단)

단순 오타·버그 수정은 기록 대상 아님 (버그 목록에만).

## 기록 포맷

```
## Decision NN: [한 줄 제목]
- 날짜: YYYY-MM-DD
- 맥락: 어떤 문제/상황에서 이 결정이 필요했나
- 결정: 무엇을 하기로 했나
- 대안: 고려했으나 버린 선택지와 버린 이유
- 근거: 왜 이 선택인가 (가능하면 수치)
- 영향: 이 결정으로 뒤따르는 변화/제약
```

## 동작
결정이 확정되면: "이건 Decision NN 후보입니다. 아래 포맷으로 추가할까요?"
라고 초안을 제시한다. 사용자 확인 후 DECISION_LOG.md에 append.
직전 번호는 파일 끝에서 확인 ("### Decision N" grep, 마지막 항목의 N+1).

## 특히 놓치기 쉬운 것
"한계를 인지하고 그대로 둔 결정"도 기록 대상이다.
예: "단일 라벨러(본인)의 한계를 인지하나, 실사용자 확보 전까지 유지" —
이런 정직한 한계 기록이 오히려 eval 성숙도의 증거가 된다.
